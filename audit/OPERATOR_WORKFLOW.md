# Operator Workflow and Acceptance Criteria

Date: 2026-08-22

## Goal

Give one operator a safe, reviewable path from lead input to CRM follow-up
without requiring them to edit JSON, inspect SQLite directly, or remember the
order of the existing command-line tools.

The interface is an orchestration layer over the existing Python workflows and
data contracts. It must not duplicate discovery, scoring, outreach, or CRM
business logic.

## Primary Workflow

### 1. Import Leads

The operator selects a supported CSV or JSON source, identifies its source type,
and previews normalized records before confirming the import.

Acceptance criteria:

- Required fields and invalid records are reported before any output changes.
- The preview shows company, canonical website/domain, location, source type,
  and source URL where available.
- Duplicate domains are merged using the existing ingestion rules.
- Confirming writes a crawl queue; cancelling writes nothing.
- Private and generated inputs are not moved into version-controlled seed data.

### 2. Run or Resume Discovery

The operator starts a controlled crawl against a selected queue and can see
domain-level progress and outcomes.

Acceptance criteria:

- Crawl limits, timeout, delay, and output locations have visible defaults.
- A run displays queued, processed, successful, and failed domain counts.
- Existing output is not replaced unless the operator explicitly chooses that
  behavior; resume/appending uses the crawler's deduplication rules.
- Interrupting a run preserves completed output and its report.
- Network, HTTP, redirect, and non-HTML failures remain distinguishable.

### 3. Review Research Failures

The operator sees unresolved domains, preserved company/branch details, failure
evidence, and the recommended research action.

Acceptance criteria:

- The research view is generated by the existing research-queue builder.
- A replacement domain requires an evidence URL, rationale, confidence, and an
  explicit reviewed decision.
- Unreviewed or low-confidence replacements cannot enter the retry queue.
- Applying reviewed resolutions retains the original domain and provenance.

### 4. Inspect Ranked Leads

The operator can sort and filter results, open a lead, and understand why it was
ranked.

Acceptance criteria:

- The list exposes company/domain, opportunity and priority measures, contact
  completeness, recommended contact method, and current CRM state.
- The detail view exposes source URLs, extracted contacts, named-person roles,
  validation evidence, missing features, and scoring explanations.
- `NOT_CHECKED` and `UNKNOWN` verification states remain explicit.
- Platform candidates and client campaign leads are visibly separate and cannot
  be silently combined.

### 5. Review Outreach Drafts

The operator reviews generated drafts and their supporting lead evidence before
approval.

Acceptance criteria:

- Draft generation never sends a message.
- Recipient, subject, body, target role, source evidence, and validation warnings
  are visible together.
- A draft without a usable public email is marked research-required and cannot
  be approved for email outreach.
- Approval records an auditable status; sending remains outside the first
  interface milestone.
- Previously sent addresses from outreach history are excluded from new drafts.

### 6. Update CRM Actions

The operator views the ordered action queue, starts one action, and completes it
with an outcome note.

Acceptance criteria:

- Starting an action uses the existing queue ordering and changes it from
  `OPEN` to `IN_PROGRESS`.
- Starting an action updates the matching lead and records an event.
- Completion requires a result note, timestamps the action, and records an
  event.
- Duplicate active actions for the same domain and action type are not created.
- A failed state transition produces a visible error and no partial update.

## First Interface Boundary

Included:

- Local, single-operator use
- Existing file-based queues, reports, scoring results, and drafts
- Existing SQLite CRM state
- Read-only evidence views and explicitly confirmed local mutations
- Progress and error reporting for long-running local jobs

Excluded:

- Email sending
- Automated replacement-domain approval
- Mailbox deliverability claims
- Phone reachability or carrier claims
- Multi-user authentication and permissions
- Hosted deployment, billing, and external CRM synchronization
- Background scheduling after the application closes

## Cross-Cutting Requirements

- The interface calls reusable Python functions; it does not shell out to CLI
  commands when a callable workflow already exists.
- File writes use the current atomic-write behavior where available.
- Actions that replace outputs or mutate CRM state require confirmation.
- Errors identify the affected record or stage without exposing credentials or
  private data.
- Every guarded action has an automated success test and a failure/no-partial-
  mutation test.
- Existing unit tests remain green.

## Definition of Done

The operator can import a small fixture dataset, crawl it with a stubbed network
client, review a simulated failure, inspect scored contact evidence, approve an
unsent draft, and start/complete a CRM action through the interface in one
end-to-end automated scenario.
